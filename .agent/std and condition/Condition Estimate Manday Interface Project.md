รายละเอียดการ Interface ระบบจัดการสต็อกและการขาย

### 1. ตาม Business Process (กระบวนการทางธุรกิจ)

กระบวนการนี้เกี่ยวข้องกับการทำงานร่วมกันระหว่าง **สำนักงานใหญ่ (ERP)**, **หน้าร้าน (POS)** และระบบ **CRM** โดยมีขั้นตอนหลักดังนี้:

*   **กระบวนการจัดการสต็อกสินค้า (Inventory Management):**
    *   การสั่งซื้อสินค้าเข้าสต็อกปกติจะทำที่ระบบ ERP (สำนักงานใหญ่) แล้วจึงทำ **ใบโอนสินค้า** มายังสาขาต่างๆ.
    *   ฝั่ง POS จะทำหน้าที่ **รับโอนสินค้า** โดยอ้างอิงจากใบขอโอนหรือใบโอนจาก ERP เพื่อเพิ่มสต็อกในสาขา,.
    *   หากมีการ **โอนระหว่างสาขา** POS ต้องแจ้งข้อมูลการโอนออกและรับเข้าให้ ERP ทราบเพื่อให้สต็อกทั้งระบบตรงกัน,.
    *   การ **ปรับปรุงสต็อก (Adjust Stock)** มักเริ่มที่ POS แล้วส่งไปให้ ERP ยืนยัน (Confirm) หากไม่ผ่านต้องทำการตรวจนับใหม่จนกว่าข้อมูลจะสอดคล้องกัน.
*   **กระบวนการจัดการข้อมูลหลัก (Master Data):**
    *   ข้อมูลสินค้า (Product), ลูกค้า (Customer) และผู้จำหน่าย (Supplier) จะถูกเตรียมไว้ และมีการส่งต่อข้อมูลเพื่อใช้เปิดใบกำกับภาษีที่หน้าสาขา.
    *   ข้อมูลสินค้ามีความซับซ้อนเนื่องจากมีหลายแพ็คไซส์ (Pack size) และหลายบาร์โค้ด ซึ่งต้อง Interface ให้ถูกต้อง.
*   **กระบวนการขายและการคืน (Sales & Return):**
    *   เมื่อมีการขายที่ POS ข้อมูลการขายทั้งแบบ **ใบกำกับภาษีอย่างย่อ (ABB)** และ **ใบกำกับภาษีเต็มรูป (Full Tax)** จะต้องถูกส่งไปที่ ERP.
    *   ในกรณีมีการคืนสินค้า จะต้องส่งข้อมูล **ใบลดหนี้ (Credit Memo/CN)** เพื่อไปปรับปรุงยอดใน ERP ด้วย.

### 2. ตามกลุ่ม ERP (แยกเส้นเข้า - เส้นออก)

การรับส่งข้อมูลกับระบบ ERP (เช่น SAP, D365, NetSweet) มีทิศทางข้อมูลดังนี้:

**เส้นข้อมูลเข้า (Inbound to POS):**
*   **ข้อมูลสินค้าและราคา:** ข้อมูลหลักของสินค้า, แพ็คไซส์, บาร์โค้ด และราคาที่กำหนดล่วงหน้า (Effective Date),,.
*   **รายการโอนสินค้า:** ข้อมูลใบโอนจากสำนักงานใหญ่เพื่อให้สาขากดรับ.
*   **ยอดสต็อกยกมา:** ในบางกรณี ERP จะส่งยอด Balance ต้นวันมาให้ POS เพื่อให้สต็อกทั้งสองฝั่งเท่ากัน.
*   **ข้อมูลลูกค้า:** สำหรับใช้ในการเปิดบัญชีหรือออกใบกำกับภาษี.

**เส้นข้อมูลออก (Outbound from POS):**
*   **ข้อมูลการขายและรายได้:** ส่งข้อมูลการขาย (ABB/Full Tax) และการคืนสินค้า (CN) ซึ่งสามารถส่งแบบ **Real-time** (แยกรายบิล) หรือ **Day-end** (รวมยอดสะสม/Lump sum),,.
*   **ข้อมูลสต็อก:** การยืนยันการรับโอน, การแจ้งโอนระหว่างสาขา และรายการปรับปรุงสต็อก (Adjust),.
*   **ข้อมูลการชำระเงิน (Payment):** ยอดการรับชำระเงิน ซึ่งอาจต้องมีการเฉลี่ยส่วนลด (Prorate) หรือแจ้งยอดปัดเศษ (Rounding) ให้ ERP ทราบ,,.

### 3. ตามกลุ่ม CRM (แยกเส้นเข้า - เส้นออก)

การ Interface กับระบบ CRM มักเน้นไปที่ข้อมูลสมาชิกและสิทธิประโยชน์ โดยใช้รูปแบบ API เป็นหลัก,:

**เส้นข้อมูลเข้า (Inbound to POS):**
*   **ข้อมูลสมาชิกเดิม:** การดึงข้อมูลสมาชิกมาแสดงผลหรืออัปเดต.
*   **การตรวจสอบคูปอง (Validate):** ตรวจสอบว่ารหัสคูปองมีอยู่จริงและสามารถใช้งานได้ตามเงื่อนไขหรือไม่,.
*   **ผลการตอบกลับ (Response):** การยืนยันสถานะการทำงานจาก Server CRM กลับมายัง POS.

**เส้นข้อมูลออก (Outbound from POS):**
*   **การลงทะเบียน (Register):** ส่งข้อมูลเมื่อมีสมาชิกใหม่สมัครที่หน้าร้าน.
*   **การอัปเดตข้อมูลสมาชิก:** เมื่อสมาชิกมีการเปลี่ยนแปลงข้อมูลส่วนตัวที่หน้าสาขา.
*   **การใช้คะแนน (Burn Point):** ส่งข้อมูลการแลกคะแนนสะสมเพื่อใช้เป็นส่วนลดหรือสิทธิพิเศษ.
*   **การยืนยันการใช้คูปอง (Confirm Coupon):** เมื่อมีการใช้งานคูปองสำเร็จ POS ต้องส่งสัญญาณไปตัดสถานะคูปองในระบบ CRM,.

**ข้อควรระวังทางเทคนิค:** การเชื่อมต่อ CRM บางเจ้าอาจไม่อนุญาตให้ POS ยิงตรง (Client to Server) แต่ต้องผ่านระบบหลังบ้าน (Server to Server) เพื่อความปลอดภัย ซึ่งอาจมีขั้นตอนการขอ Token ก่อนเริ่มส่งข้อมูล,,.
-------------------------------------------------
แนวทางการคำนวณ Man-day (วันทำงาน) สำหรับการพัฒนาระบบอินเทอร์เฟซในกลุ่มเอกสารต่างๆ ตามที่ระบุในแหล่งข้อมูล มีรายละเอียดการประเมินโดยอิงจากมาตรฐานของ **Senior Programmer** ดังนี้ครับ:

### 1. กลุ่มข้อมูลหลัก (Master Data)
กลุ่มนี้มีความซับซ้อนเนื่องจากโครงสร้างข้อมูลที่ต้องรองรับความหลากหลายของสินค้า:
*   **ข้อมูลสินค้า (Product Master):** ประเมินไว้ที่ **4 - 5 วัน** เนื่องจากความซับซ้อนของโครงสร้าง เช่น สินค้าหนึ่งรายการมีหลายแพ็คไซส์ (Pack size) และแต่ละแพ็คไซส์มีหลายบาร์โค้ด
*   **ข้อมูลราคา (Price):** หากมีการส่งราคาจาก ERP มาด้วย ให้บวกเพิ่ม **3 วัน** แต่หากตั้งราคาที่ POS เองก็ไม่ต้องนำส่วนนี้มาคำนวณ
*   **ข้อมูลลูกค้า (Customer Master):** ประเมินไว้ที่อย่างน้อย **3 วัน**
*   **ข้อมูลผู้จำหน่าย (Supplier):** ส่วนใหญ่ไม่ทำอินเทอร์เฟซ แต่มักใช้วิธีการ Initial ข้อมูลตั้งต้นแทน

### 2. กลุ่มเอกสารจัดการสต็อก (Inventory Management)
*   **เอกสารรับโอน/จ่ายโอน (Inventory Transfer):** ประเมินไว้ที่ **3 วัน** ต่อประเภทเอกสาร
*   **เอกสารที่มีความซับซ้อนสูง:** เช่น ใบรับของ, ใบซื้อ หรือ Invoice (กรณีทำที่ POS) อาจต้องปรับเพิ่มจาก 3 วัน เป็น **4 วัน**
*   **การปรับปรุงสต็อก (Adjust Stock):** มักประเมินรวมในกระบวนการสต็อก ซึ่งต้องมีการส่งข้อมูลไปให้ ERP ยืนยัน (Confirm)

### 3. กลุ่มเอกสารการขายและชำระเงิน (Sales & Payment)
เป็นกลุ่มที่มีเงื่อนไขทางภาษีและรายละเอียดบิลเข้ามาเกี่ยวข้องมาก:
*   **ข้อมูลการขาย (Sales - ABB/Full Tax):** ประเมินไว้ที่ **4 - 5 วัน** เนื่องจากมีความซับซ้อนสูง
*   **การคืนสินค้า (Sales Return/CN):** ประเมินไว้ที่ **2 - 3 วัน** (ลดลงจากใบขายเพราะใช้โครงสร้างคล้ายกัน)
*   **ใบกำกับภาษีเต็มรูป (Full Tax):** หากแยกจากใบขาย ประเมินไว้ที่ **3 วัน** (รวมการจัดการข้อมูลลูกค้า) และใบคืนภาษีประเมินที่ **1.5 วัน**
*   **เงินมัดจำ (Deposit):** ประเมินที่ **3 วัน** และการคืนเงินมัดจำที่ **1.5 วัน**
*   **ใบสั่งขาย (Sale Order):** หากจำเป็นต้องส่ง ประเมินที่ **3 วัน**

### 4. กลุ่มระบบ CRM และสิทธิประโยชน์
*   **การเชื่อมต่อพื้นฐาน:** เช่น การสมัครสมาชิก (Register), อัปเดตข้อมูล หรือการใช้แต้ม (Burn Point)
*   **การขอ Token/Authentication:** หาก API ต้องมีการขอ Token ทุกครั้ง ให้บวกเพิ่มอีก **1 เส้น (1 วัน)** เพื่อจัดการระบบความปลอดภัย
*   **Middleware (Server-to-Server):** กรณี CRM ไม่ให้ Client ยิงตรง ต้องผ่าน Server ของเราก่อน ให้บวกเพิ่ม **1.5 - 2 วัน** ต่อเส้น

### 5. ส่วนงานระบบหลังบ้าน (Store Back Office)
ทุกโครงการที่มีอินเทอร์เฟซจำเป็นต้องมีหน้าจอจัดการ ดังนี้:
*   **หน้าจอ Setup/Config:** สำหรับ Mapping ข้อมูล ประเมิน **3 - 4 วัน**
*   **หน้าจอ Manual Import:** ประเมิน **2 วัน**
*   **หน้าจอ Manual Export:** ประเมิน **2 วัน**
*   **หน้าจอประวัติ (History/Log):** ประเมิน **2 วัน**
*   **การตั้งเวลา (Task Schedule/Trigger):** สำหรับโหมด Auto/Manual ประเมินที่ **0.5 วัน ต่อ 1 เส้นเอกสาร**

### ข้อควรระวังเพิ่มเติมในการประเมิน
*   **ระดับนักพัฒนา:** หากใช้ **Junior Programmer** แนะนำให้บวกเพิ่ม (Charge) จากยอดรวมอีกประมาณ **10%**
*   **ฟังก์ชันเสริม:** การส่งแจ้งเตือนผ่าน Email หรือ Line Notification ให้บวกเพิ่ม **2 - 3 วัน**
*   **ความดิฟของตัวเลข:** ต้องเผื่อเวลาสำหรับการจัดการเรื่อง **Prorate (การเฉลี่ยส่วนลด)** และ **การปัดเศษ (Rounding)** เพื่อไม่ให้ตัวเลขใน ERP และ POS ต่างกัน
=======================================================
ในการคำนวณ Man-day สำหรับโครงการ Interface ระบบมีปัจจัยด้าน **System Impact** หรือผลกระทบเชิงระบบที่สำคัญหลายประการที่ต้องนำมาพิจารณาเพิ่มเติม เนื่องจากปัจจัยเหล่านี้ส่งผลโดยตรงต่อความซับซ้อนและระยะเวลาในการพัฒนา ดังนี้ครับ:

### 1. โครงสร้างพื้นฐานและการเชื่อมต่อ (Infrastructure & Connectivity)
*   **รูปแบบการรับส่งข้อมูล (Middleware/Server-to-Server):** หากระบบ CRM หรือ ERP ไม่อนุญาตให้ Client (POS) เชื่อมต่อตรง แต่บังคับให้ผ่าน Server-to-Server (Middleware) จะต้องบวกเวลาเพิ่ม **1.5 - 2 วัน** ต่อเส้นทางข้อมูล
*   **ระบบความปลอดภัย (Authentication):** หาก API ต้องการการขอ **Token** ทุกครั้งก่อนเริ่มการรับส่งข้อมูล จะต้องบวกเพิ่มอีก **1 วัน (หรือ 1 เส้น)** เพื่อจัดการระบบความปลอดภัยนี้
*   **ประเภทของฐานข้อมูลและไฟล์:** ความยากง่ายขึ้นอยู่กับประเภท Database (เช่น Oracle, MSSQL, MySQL) และรูปแบบไฟล์ (เช่น JSON, XML, CSV) รวมถึงช่องทางที่ใช้ (FTP, SFTP, หรือ Web Service)

### 2. ความซับซ้อนของลอจิกธุรกิจ (Business Logic Complexity)
*   **การจัดการส่วนลดและเศษสตางค์ (Prorate & Rounding):** เป็นจุดที่ต้องระวังสูงที่สุด หากต้องมีการเฉลี่ยส่วนลดท้ายบิลลงไปในรายสินค้า (Prorate) หรือการจัดการการปัดเศษ (Rounding) เพื่อให้ยอดรวมระหว่าง POS และ ERP ตรงกัน จะต้องเผื่อเวลาในการคำนวณและทดสอบอย่างมาก
*   **ความละเอียดของทศนิยม (Decimal Precision):** หากระบบต้นทางและปลายทางใช้จำนวนหลักทศนิยมต่างกัน (เช่น POS เก็บ 4 ตำแหน่ง แต่ ERP รับ 2 ตำแหน่ง) จะส่งผลต่อการดิฟ (Diff) ของตัวเลข ซึ่งต้องมีแผนรองรับที่ชัดเจน
*   **เงื่อนไขทางภาษี (Tax Handling):** ต้องตรวจสอบว่าราคาส่งมาเป็นแบบรวมภาษี (Include) หรือแยกภาษี (Exclude) รวมถึงการจัดการสินค้าที่ไม่มีภาษี (เช่น สินค้า OTOP) ซึ่งมีผลต่อลอจิกการคำนวณในใบซื้อหรือใบรับของ

### 3. การจัดการข้อมูลหลักและราคา (Master Data & Pricing)
*   **โครงสร้างสินค้า (Product Structure):** สินค้าที่มีความซับซ้อน เช่น 1 รายการมีหลายแพ็คไซส์ (Pack size) และแต่ละแพ็คไซส์มีหลายบาร์โค้ด จะใช้เวลาพัฒนามากกว่าปกติ (ประเมินไว้ที่ 4-5 วัน)
*   **เงื่อนไขราคา (Effective Date):** หากระบบต้องรองรับการตั้งราคาล่วงหน้าที่มีผลตามวันที่กำหนด (Effective Date) หรือราคาโปรโมชั่นช่วงเวลา (Play Off) จะเพิ่มความซับซ้อนในการ Interface ข้อมูลราคา

### 4. ปริมาณข้อมูลและข้อจำกัดของระบบ (Data Volume & Limits)
*   **ข้อจำกัดในการรับส่ง (Transmission Limits):** ต้องคำนึงถึง Maximum Limit ของจำนวน Record ต่อการส่งหนึ่งครั้ง หากข้อมูลมีปริมาณมากจนเกินขีดจำกัดของ API หรือไฟล์ ปลายทางอาจรับไม่ได้ ซึ่งต้องเสียเวลาในการพัฒนาลอจิกเพื่อแบ่งไฟล์หรือแบ่งการส่งข้อมูล (Split Data)

### 5. ส่วนงานสนับสนุนและฟังก์ชันเสริม (Operational & Extra Functions)
*   **หน้าจอจัดการหลังบ้าน (Back Office Screens):** ทุกโครงการ Interface จำเป็นต้องมีหน้าจอ Setup/Config (3-4 วัน), หน้าจอ Manual Import/Export (อย่างละ 2 วัน) และหน้าจอประวัติ (2 วัน) เพื่อใช้บริหารจัดการเมื่อระบบอัตโนมัติมีปัญหา
*   **การแจ้งเตือน (Notifications):** หากต้องการให้ระบบส่ง Email หรือ Line แจ้งเตือนเมื่อเกิดข้อผิดพลาดในการ Interface ต้องบวกเพิ่มอีก **2-3 วัน**
*   **การตั้งเวลาทำงาน (Task Scheduler):** AdaTask จะจัดการตัวกระตุ้น (Trigger) ให้ระบบทำงานแบบอัตโนมัติในโหมด Auto (MQ Background Process)ประเมินไว้ที่ **0.5 วัน ต่อ 1 เส้นเอกสาร**
Man day ที่เราประเมิน ว่าเป็น process แต่ละเส้น มักจะอยู่ใน MQ Background Process
